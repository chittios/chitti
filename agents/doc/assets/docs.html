Documentation

How an OS is arranged when an agent — not a binary — is the thing you run.

The determinism boundary

The load-bearing invariant. Model output is an untrusted plan; it is parsed, grammar-validated, capability-checked, scope-checked, taint-gated, and only then executed by deterministic native code (Synapse). Above the boundary: stochastic. Below: deterministic and audited.

Agents as installable apps

An agent is "programmed" in markdown — a SOUL.md persona, skill docs, and a manifest declaring its toolset (= permissions), UI/network access, and optional models. Install from a public registry with a per-capability consent prompt that can only ever narrow what the package requested:

/agents search  https://registry/index
/agents install doc --registry https://registry/index
/agents list

Channels

Capability-gated byte-stream and datagram IPC between agents — the Linux pipe/socket analog. A handle is an unforgeable capability resolved in the caller's own table, never an ambient global id. A service agent can hand an accepted TCP connection to another agent as an ordinary channel.

Service agents

Long-running native daemons. The Network agent listens and forwards connections; the Doc agent (serving this page) parses HTTP/1.1 natively and reads its documents from its own install folder; the SSH agent handles the transport. Protocol logic is deterministic native code — the model plans policy over capabilities, it never implements a protocol.

/agents start doc 8080
/agents services

Least privilege

Delegation only ever narrows authority, and a skill or agent is bounded by its install-time grant forever. This Doc agent, for instance, holds only read access to its own install folder and memory — enough to serve its pages, nothing more.
